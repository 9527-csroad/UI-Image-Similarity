# Phase 3 产品分析 + Phase 4 需求

## 1. Phase 3 测试结果

| Case | 描述 | Phase 2 | Phase 3 | 预期 | 判定 |
|------|------|---------|---------|------|------|
| A | 深色音乐 App vs 浅色新闻 Feed | 29.3% | 34.6% | <20% | 不达标（且比 Phase 2 更差） |
| B | 白色充电列表 vs 主题商店 | 64.3% | 44.1% | <35% | 偏高 |
| C | 同一布局，不同卡片内容 | 61.4% | 65.5% | 55-70% | **达标** |
| D | 插画页 vs 设置对话框 | 47.1% | 33.6% | <25% | 偏高 |
| E | 锁屏时钟 vs 主题商店 | — | 41.0% | <30% | 偏高 |
| F | 教程详情页 vs 标签设置页 | — | 58.6% | <25% | **严重偏高** |

6 个用例中仅 1 个达标。核心问题：**iOS 系统框架元素（status bar、nav bar、tab bar、home indicator）在所有维度上贡献了"相似度地板"**。

## 2. 核心问题

**"布局相似" ≠ "抄袭"**。所有 iOS App 都遵循 Human Interface Guidelines (HIG)，天然有相似框架。真正的抄袭判断应该基于：**两个 App 的 UI 组件（按钮、图片、文字块、卡片）是否在位置和样式上高度一致**。

## 3. Phase 4 优化需求

### PRD-001: iOS 框架区域检测与排除（P0 - 必须）
自动检测并排除 status bar、nav bar、bottom safe area、tab bar 区域。
- 推荐基于**边缘密度自适应检测**，而非固定比例裁剪
- 验证标准：排除后 dHash 对不相关页面 <40%

### PRD-002: dHash 框架噪声消除（P0 - 必须）
dHash 计算前排除框架区域，使 dHash 真正反映内容布局。
- 如果 P0 已实施，dHash 权重可从 10% 降至 5% 或 0%

### PRD-003: SSIM 内容掩码修正（P0 - 必须）
iOS chrome 区域不应贡献正向相似度。在内容掩码基础上，额外排除检测到的 chrome 区域。

### PRD-004: Edge 网格框架排除（P1）
8x8 网格排除顶部和底部的框架行。

### PRD-005: 空间颜色框架排除（P1）
4x4 颜色网格排除顶部和底部框架行。

### PRD-006: 权重重新校准（P0）
在排除框架后重新校准各指标权重。增加 SSIM 和 Edge 的相对权重。

### PRD-007: 测试基准建立（P0）
建立至少 8 对标准化测试图像，覆盖 4 个相似度层级，作为后续优化的回归基准。

## 4. 三方讨论共识

### 4.1 核心策略
- **iOS Chrome 自适应剥离**（自底向上检测：home indicator → tab bar → nav bar → status bar）
- **dHash 默认权重 0%**（保留配置项，实测后可恢复至 5%）
- **权重调整**：内容 45%（SSIM）+ 布局 30%（Edge 8x8）+ 风格 15%（Spatial 10% + Dominant 5%）
- **分歧惩罚改为诊断信号**，不直接修改综合分

### 4.2 测试基准扩展至 10 对
新增 G（同页不同时间）、H（同类功能不同布局）、I（全屏无 chrome）、J（深色 vs 浅色）。

### 4.3 不可妥协的要求
- 不在 chrome 噪声消除前调整权重或引入降权因子
- 不引入深度学习模型、不增加新维度
- 所有魔法数字必须有实证基础
- Case F（最严重误判）必须降至 <25%

## 6. 给研发团队的指令

**核心任务：消除 iOS 框架元素污染。**
优先级：(1) Chrome 检测器 + 裁剪 → (2) 权重重新校准 + 掩码 → (3) 全量验证

**不要**：引入深度学习模型、增加新维度、在不消除噪声的前提下调权重。
