# 算法演化报告

## 1. 目标

检测 iOS App UI 截图之间的抄袭相似度。判断两张 UI 截图是"同一界面的抄袭"还是仅"共享 iOS 通用框架"。

核心判定标准：
- **是抄袭**：相同的信息架构 + 组件布局 + 视觉风格
- **不是抄袭**：仅共享 iOS HIG 通用组件（status bar、nav bar、tab bar、home indicator）

## 2. 算法演化历程

### Phase 1（初始版）

- **算法组成**：SSIM（50%，全图彩色 SSIM）+ dHash 16x16（25%）+ 全局 HSV 颜色直方图（25%）
- **核心问题**：
  - 白底页面（如设置页、列表页）相似度虚高，SSIM 被 75% 的空白背景"劫持"——两个完全不同的白底页面因大面积相同背景色而获得高分
  - dHash 16x16 对移动端截图粒度过粗，无法区分细节差异
  - 全局颜色直方图丢失空间信息，无法区分"上黑下白"和"上白下黑"
- **根因**：全部指标都在整图范围计算，没有区分"内容区域"和"空白背景"。

### Phase 2（多指标）

- **新增算法**：
  - pHash 16x16（10%）替换部分 dHash 权重
  - Edge 相似度（25%）：4x4 空间网格 + 4-bin 方向直方图
  - Spatial color（25%）：4x4 网格，每格 H-S 二维直方图，CHI-SQUARE 距离
  - Dominant color（10%）：K-means k=5，CIELAB 双向匹配
  - SSIM 权重降至 30%
- **解决的问题**：
  - 4x4 空间颜色网格引入了位置信息，能区分"顶部深色底部浅色"vs"顶部浅色底部深色"
  - Edge 网格 + 方向能区分"列表视图（水平边为主）"vs"弹窗（多方向混合）"
  - Dominant color 对主题色变化敏感
- **引入的新问题**：
  - pHash 16x16 太粗糙，所有手机截图都呈现"深色顶部 + 浅色中间 + 深色底部"三段式模板，pHash 把它们当成同一类
  - **整体方案奖励的是"共享 UI 模板"而非"同一 UI 身份"**——任何两张遵循 iOS HIG 的截图都会拿到不低的分数

### Phase 3（内容感知）

- **核心改进**：
  - **SSIM 内容掩码**（权重 35%）：Sobel 梯度检测纹理/边缘区域，将均匀背景设为中性灰 128，只比较"有内容"的区域
  - **dHash 替换 pHash**（权重 10%）：dHash 基于相邻像素梯度比较，比 DCT 的 pHash 更能捕捉 UI 元素边界
  - **Edge 升级为 8x8 网格**（权重 25%）：4x4 -> 8x8（64 cell），分辨率翻倍，能更好区分布局差异
  - **内容密度门控**：两张图内容复杂度差异大时，自动降分
  - **指标分歧惩罚**：各子指标标准差 > 30 时降分，防止"一项极高 + 一项极低"平均出误导性的中间值
  - **主题切换检测**：Edge 高 + 颜色低时识别为 theme swap
- **解决的问题**：
  - SSIM 不再被大面积白底/黑底劫持，只关注有纹理的内容区域
  - 8x8 边缘网格提供了更精细的空间分辨率
  - 内容密度门控能区分"纯文本列表"vs"插画页面"
- **残留问题**：
  - dHash 仍然给完全不相关的页面打出 70-82% 的高分（见 Case B/E/F）
  - iOS 通用框架元素（status bar / nav bar / safe area）在多项指标中持续贡献"相似度地板"
  - Case F（教程页 vs 标签设置页）综合分 58.6%，远超预期 <30%

## 4. 核心问题诊断

### 4.1 iOS Chrome 的"相似度地板"效应

所有 iOS 截图共享以下结构性元素（约占画面的 25-35%）：

| 区域 | 位置 | 高度（pt） | 内容 | 影响 |
|------|------|-----------|------|------|
| Status bar | 顶部 | ~44pt | 时间、电池、信号 | 所有截图几乎相同 |
| Navigation bar | 顶部 status bar 下方 | 44-96pt | 返回按钮、标题、右侧操作 | 结构高度一致 |
| Tab bar | 底部 home indicator 上方 | ~80-100pt | 3-6 个 tab 图标 | 常见布局，跨 App 复用 |
| Home indicator | 底部 | ~34pt | 横条 | 所有截图相同 |

这些 chrome 元素在各项指标中的影响：

- **SSIM 内容掩码**：iOS chrome 中的图标和文字会产生 Sobel 梯度边 -> 被判定为"内容"而非背景 -> 两张不同截图的 status bar / nav bar 区域被当作"相同内容"参与 SSIM 计算
- **dHash 16x16**：将 16x16=256 个梯度比较压缩为一个哈希值。status bar 的横线、nav bar 的分隔线、tab bar 的图标排列，这些 iOS 通用元素占据了哈希的大部分有效位。**这就是为什么完全不相关的两张 iOS 截图 dHash 能到 70-82%**——它们的 chrome 框架哈希几乎相同
- **Edge 8x8 网格**：顶部 1-2 行格子（status bar + nav bar 区域）和底部 1 行格子（safe area / tab bar）在任意两张 iOS 截图中都有相似的边缘分布，贡献了固定的基础相似度

### 4.2 根本矛盾

当前所有指标都是**"像素/梯度级别"的全局比较**，缺少对"什么是 UI 组件"的语义理解。算法看到的是一堆梯度和颜色分布，无法区分：
- "这是 iOS 系统的 status bar，应该忽略"
- "这是一个自定义的卡片组件，应该重点比较"

Edge 8x8 衡量的是**宏观布局模式**（整体边缘分布），不是组件级的精确位置关系。8x8 网格（64 个格子）无法区分"三个卡片水平排列"和"三个卡片垂直排列"如果它们占据相同的宏观区域。因此，布局分更准确的描述是"宏观布局模式相似度"，而非"组件位置关系"。

这导致算法在**结构层面**（都有 status bar + nav bar + content area + tab bar）给出天然的高相似度，而不是在**组件层面**（两个页面的按钮、图片、文字块是否相同）做判断。

## 5. Phase 4 优化方案（三方确认版）

### 5.1 核心思路

iOS Chrome 自适应剥离（自底向上检测 + 内容区域独立裁剪）+ 指标权重重新校准 + chrome 区域零权重掩码。

**实施原则**：先消除 chrome 噪声，再讨论权重。所有参数改为可配置项，不硬编码魔法数字。

### 5.2 具体方案

#### 方案 A：iOS Chrome 自适应检测与剥离

**检测策略（自底向上）**：

UI 工程师明确指出检测顺序应为自底向上，因为底部区域（home indicator）在所有现代 iOS 设备上最稳定，顶部区域变化最大（largeTitle vs 标准 nav bar vs 无 nav bar）。

| 检测步骤 | 检测目标 | 检测方法 | 高度范围 |
|----------|---------|---------|---------|
| 1 | Home indicator | 底部 0-34pt 区域检测细长水平条（高宽比 >10:1 的深色/浅色矩形） | 底部 ~34pt |
| 2 | Tab bar | home indicator 上方 34-134pt 区域，检测周期性边缘密度模式（3-6 个 tab 的间隔特征），不计数具体图标 | 底部 ~80-100pt |
| 3 | Navigation bar | 从顶部向下扫描，寻找第一个"非内容区域"——即边缘密度呈现水平带状且下方有明显内容边界的区域 | 顶部 ~44-96pt |
| 4 | Status bar | nav bar 上方 0-44pt 区域，检测为从顶边界开始的第一个非内容带（不依赖识别具体图标模式） | 顶部 ~44pt |

**自适应适配**：

- **largeTitle nav bar**：检测到 nav bar 区域内有大面积文字密度时，自动扩展裁剪范围至 ~96pt
- **无 tab bar 页面**：跳过 tab bar 检测，底部仅裁剪 home indicator
- **无 status bar 页面**（全屏游戏/视频）：跳过 status bar 检测
- **非 iOS 截图回退**：若以上四个步骤均未检测到明确 iOS chrome 特征（边缘密度模式不匹配），自动降级为"不裁剪"模式。适用于 Android、Web、桌面应用截图。
- **回退策略**：若检测器置信度低于阈值（可配置，默认 0.6），回退到固定比例裁剪（顶部 15% + 底部 12%），并记录警告日志。

**裁剪后内容区域**：nav bar 下边界 -> tab bar 上边界（或 home indicator 上边界，若无 tab bar）。

#### 方案 B：指标权重重新校准

采纳产品与 UI 的共同建议，权重调整如下：

| 指标 | Phase 3 权重 | Phase 4 权重 | 调整理由 |
|------|-------------|-------------|---------|
| SSIM（内容） | 35% | **45%** | 裁剪 chrome 后 SSIM 专注于真实内容，权重提升 |
| Edge 8x8（布局） | 25% | **30%** | UI 建议降至 25-30%，取中间值。明确定义为"宏观布局模式" |
| Spatial Color + Dominant Color（风格） | 35% | **15%** | 产品和 UI 一致认为 4x4 分辨率太粗糙，从 25% 降至 15% |
| dHash | 10% | **可配置，默认 0%** | 产品明确要求"先实施 chrome 裁剪，实测后再定"。Phase 4 初始版本设为 0%（完全移除），保留配置项以便后续恢复 |

**关于 dHash 的具体决策**：
- Phase 4 初始版本将 dHash 权重设为 0%，等同于移除
- 保留 `dhash_weight` 配置参数（默认 0.0），可在 `config.json` 中修改
- chrome 裁剪完成后，若实测显示 dHash 对不相关页面 <40%，可恢复至 5%；若 >50%，保持 0%
- 这是对产品"不应预设权重"和"数据驱动"要求的直接响应

**关于风格分权重**：
- 产品建议"不超过 15%"，UI 建议 15%，取 15%
- Spatial Color（4x4 网格）和 Dominant Color 合并为风格子维度，共 15%
- 其中 Spatial Color 占 10%，Dominant Color 占 5%

**最终权重公式**：

```
综合分 = SSIM * 0.45 + Edge * 0.30 + Style * 0.15 + dHash * dhash_weight(默认0.0)
```

#### 方案 C：Chrome 区域掩码

在计算 dHash（若恢复）和 Edge 8x8 时，对 chrome 区域施加零权重掩码，作为方案 A 裁剪策略的双重保险：

- **dHash chrome 掩码**：计算前将 chrome 区域填充为中性灰（128），使其不贡献梯度信息
- **Edge 8x8 chrome 掩码**：在 8x8 网格中，落在 chrome 区域内的格子权重设为 0，不参与相似度计算
- **SSIM chrome 掩码**：与现有的 Sobel 内容掩码叠加，chrome 区域额外设为中性灰

**注意**：方案 C 是方案 A 的补充而非替代。方案 A（物理裁剪）是主力，方案 C（掩码）处理裁剪边缘的过渡区域。

#### 方案 D：品牌色降权因子（数据驱动版）

产品要求所有魔法数字必须有实证基础。Phase 4 采取以下策略：

- **Phase 4 初始版本不引入品牌色降权因子**（0.85 系数）和**分歧惩罚降分**（10%），原因：
  1. 这些参数（阈值 0.5、系数 0.85、分歧阈值 30、降分 10%）没有实证数据支撑
  2. 产品明确要求"不要在不消除噪声的前提下调权重"——当前 chrome 噪声尚未消除，引入额外降权因子违反优先级
  3. 三维度分歧惩罚与品牌色降权叠加可能导致过度降分（最多约 23.5%），缺乏精细控制

- **Phase 4 后续迭代**（chrome 裁剪验证完成后）：
  1. 基于 10 对测试用例的实测结果，统计分析品牌色差异与综合分的关系
  2. 若发现"布局/内容相似但品牌色完全不同"的 case 综合分仍然过高，再引入降权因子
  3. 所有参数的推导过程必须文档化，包含实测数据表和 ROC 曲线

#### 方案 E：分歧惩罚保留但调整

Phase 3 的"指标分歧惩罚"（标准差 >30 时降分）改为：

- 仅作为**诊断信号**输出到响应中（如 `"warning": "high_divergence_between_metrics"`），不直接修改综合分
- 前端可据此展示额外提示（如"布局相似但内容不同"），但不影响核心评分
- 这保留了 Phase 3 的多指标不一致检测能力，同时避免了"无实证降权"的问题

### 5.5 实施步骤

**Phase 4 分两个阶段实施**：

**第一阶段：Chrome 检测器 + 裁剪（P0，核心）**

1. 新建 `chrome_detector.py`：
   - `detect_home_indicator(image) -> (y_start, y_end, confidence)`
   - `detect_tab_bar(image, home_indicator_top) -> (y_start, y_end, confidence)`
   - `detect_nav_bar(image) -> (y_start, y_end, confidence, is_large_title)`
   - `detect_status_bar(image, nav_bar_bottom) -> (y_start, y_end, confidence)`
   - `detect_all(image) -> content_region (crop_bounds)`：按自底向上顺序调用，返回内容区域边界

2. 新增 `crop_content_region(image, crop_bounds) -> cropped_image`

3. 修改 `compare_images()` 流程：
   - 在计算任何指标前，先对两张图分别执行 chrome 检测与裁剪
   - 将裁剪后的内容区域传入现有指标计算管道

4. 新增 `chrome_debug_overlay(original_image, crop_bounds) -> debug_image`：
   - 在原图上用彩色框标注检测到的 chrome 区域
   - 用于可视化验证裁剪结果是否正确

5. 对 6 个核心用例执行可视化验证，确认裁剪结果正确后才进入第二阶段

**第二阶段：权重调整 + 掩码（P1，验证通过后）**

6. 将所有权重参数移至 `config.json`，不再硬编码
7. dHash 权重默认设为 0.0
8. 实现 chrome 区域掩码（方案 C）

### 5.6 风险与限制

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Chrome 检测器对低分辨率/模糊截图误判 | 裁剪范围错误，内容区域被误删或 chrome 残留 | 回退到固定比例裁剪；可视化验证工具辅助排查 |
| Case F 裁剪后 SSIM 仍 >30% | 综合分可能 >25%，达不到产品目标 | 扩大 chrome 检测范围；或进一步降低 SSIM 权重 |
| 非 iOS 截图被误识别为有 chrome | 正常内容被裁剪 | 检测置信度阈值（0.6）+ 回退模式 |
| largeTitle nav bar 与内容区域边界模糊 | 裁剪不精确 | 使用文字密度检测区分 largeTitle 区域 |
| Edge 8x8 仍只能衡量"宏观布局模式" | 无法区分组件级抄袭 | 已明确声明此为限制，组件级匹配留给 Phase 5+ |
| dHash 设为 0% 后丢失部分区分能力 | 极少数 case 可能漏检 | 保留配置项，实测后可恢复至 5% |
| 4x4 风格网格太粗糙 | 风格分可能引入噪声 | 权重已降至 15%，影响有限 |

**已知不做的事项（Phase 4 范围外）**：
- 不引入深度学习模型
- 不增加新的比较维度（仅使用现有 5 个指标）
- 不做 OCR 文字识别（Phase 5+）
- 不做组件级精确匹配（Phase 5+）
- 不在 chrome 噪声消除前调整权重或引入降权因子
